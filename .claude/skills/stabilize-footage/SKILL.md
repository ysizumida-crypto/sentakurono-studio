# stabilize-footage — 手ブレ補正(バーチャル三脚)

くろのんチャンネルの那智の滝素材の固定で確立(2026-08-03)。
**最重要の教訓**: vid.stab で処理しただけの素材を「固定済み」と信じて30本以上を納品したが、実測すると残存ブレは**平均42.8px・最大235px**でほぼ無補正だった。視聴者は酔う。**実測なしに固定済みと判断してはいけない。**

## 手順の全体像

```
1. 計測   scripts/measure_shake.py <入力>          → ブレの大きさを知る
2. 選択   ブレ量と視差の有無から手法を決める        → 下の「手法の選び方」
3. 補正   scripts/lock_footage.py または vid.stab
4. 検証   scripts/measure_shake.py <出力>          → 平均1px未満なら合格
```

検証は省略できない。3 の出力に対して必ず 1 と同じ計測をかけ、**補正前後の数値を並べて報告する**。

## 手法の選び方

`measure_shake.py` が出す「最大移動量」で決める。

| 実測値 | 手法 | 理由 |
|---|---|---|
| 〜50px・平面的な被写体 | ffmpeg vid.stab(下記) | 手軽。補正幅 zoom=10 (=10%) に収まる |
| 50px超、または奥行きのある風景 | **`scripts/lock_footage.py`(推奨)** | vid.stab の補正幅を超える。かつ相似変換では視差を除去できない |
| 動きを残したい(パン・歩き撮り) | vid.stab 通常モード | 完全固定は不自然になる |

判断に迷ったら `lock_footage.py` を使う。軽い素材でも問題なく効く。

## 絶対固定(scripts/lock_footage.py)

`pip install numpy opencv-python-headless` が必要(未導入なら自動で入れてよい)。

```bash
python3 scripts/lock_footage.py 入力.mp4 出力.mp4 --crop CX CY CW CH --order 3
```

`--crop` は**最終的に画面に映る矩形**を入力動画の座標で指定する。この範囲の固定精度を最優先で最適化するため、指定は仕上がりに直結する。省略すると全画面を対象に、黒縁の入らない最大矩形を自動算出する。

仕組みと、なぜこの順序でなければならないか:

1. **順逆追跡で動く被写体を捨てる** — 基準コマ→現コマ→基準コマ とオプティカルフローを往復させ、戻り位置が 0.3px 以上ずれる点を捨てる。滝の水・炎・波・葉ずれは往復が破綻するので自動的に落ち、岩・建物・地面だけが基準として残る。マスクを手描きする必要がない。
2. **ロバスト2〜3次多項式で視差ごと吸収する** — 手持ち撮影ではカメラ位置そのものが動くため、手前の被写体と奥の被写体は**異なる量**動く(視差)。相似変換(平行移動+回転+拡大)は全画素に同じ動きを仮定するので、原理的に視差を消せない。実測でも相似変換では平均2.6pxで頭打ちになり、2次で0.96px、3次で0.68pxまで落ちた。多項式は「画面内で滑らかに変化する動き」を表現できるのでこれが効く。
3. **残差トリミングで通行人を除外** — 当てはめ→残差の大きい点を捨てる→再当てはめ、を5回繰り返す。人物など局所的に動くものはここで落ちる。

出力は指定矩形をそのまま切り出す。`切り出しの余裕 = -N px` と表示されたら黒縁が入るので、矩形を N px 以上内側に詰めて再実行する。

## 検証(scripts/measure_shake.py)

```bash
python3 scripts/measure_shake.py 出力.mp4
```

基準コマに対する各コマの特徴点移動量(中央値)を出す。読み方:

- **平均 1px 未満** = 合格。1080p に合成しても知覚できない
- **平均 3px 以上** = まだ揺れる。視差が残っているので `--order 3` を試すか、切り出し矩形を狭める
- **平均 10px 以上** = 補正が効いていない。手法の選択から見直す

`--scan` を付けると素材全体を走査し、最も揺れの少ない区間を秒単位で報告する。使える区間を選び直せる場合に有効。

参考実測値(那智の滝・iPhone手持ち13秒):

| 状態 | 平均残存ブレ | 最大 |
|---|---|---|
| vid.stab tripod 処理後(旧) | 42.8px | 235.2px |
| 相似変換で絶対固定 | 2.6px | 7.5px |
| **3次多項式で絶対固定(採用)** | **0.68px** | 1.81px |

## ffmpeg vid.stab(軽い素材向け)

```bash
# パス1: 検出
ffmpeg -y -ss <開始> -t <秒数> -i input.mov \
  -vf "vidstabdetect=tripod=1:shakiness=10:accuracy=15:result=stab.trf" -f null -
# パス2: 変換
ffmpeg -y -ss <開始> -t <秒数> -i input.mov -an \
  -vf "vidstabtransform=tripod=1:input=stab.trf:zoom=10:optzoom=0:interpol=bicubic:crop=black" \
  -c:v libx264 -preset fast -crf 18 -pix_fmt yuv420p stabilized.mp4
```

通常モード(動きを残す)はパス1の `tripod=1` を外し、パス2を `vidstabtransform=input=stab.trf:smoothing=30:zoom=5` にする。

注意点:

- **-ss/-t は両パスで同一にする**(検出と変換でコマがずれると破綻する)
- `zoom=10` は補正幅が元画角の10%しかない。それを超える手ブレは**そのまま残る**。処理が成功したように見えても補正されていないので、必ず実測する
- iPhone 等の縦位置素材は回転メタデータを持つ。OpenCV は回転を適用しないので、`ffmpeg` で一度書き出して正立させてから処理する

## 完成品の検査(scripts/find_jumps.py)

素材を固定しても、**合成の段階で画が飛ぶ**ことがある。素材の検証とは別に、完成した動画でも測る。

```bash
python3 scripts/find_jumps.py 完成.mp4 X Y W H 1.5
```

隣り合うコマ同士のズレを位相相関で測り、突出した箇所を秒で報告する。`X Y W H` は測る領域で、**文字の載る範囲を避ける**と映像だけの動きが見える(テロップの切り替わりも「跳び」として出てしまうため)。

読み方:

- **相関値が 0 付近** = 前後のコマが別物。素材が抜けているか切り替わっている
- 意図的なフェードイン・アウトも跳びとして出る。冒頭・末尾の検出は無視してよい

### 実例: 窓の映像が一瞬消える

くろのんの特別編で「途中で画面が動く」と指摘された。調べると、10カット中3カットの**先頭1〜2コマだけ窓の映像が抜け**、背景が素通しになっていた(滝が一瞬消える)。

原因は `-ss` と `overlay` の組み合わせ。`-ss` はコマ境界の途中を指すため、副入力の最初のコマが t=0 に間に合わず、overlay がその間だけ主入力をそのまま出す。**エラーは出ない。**

```
# 直し方: 副入力の時刻を 0 に貼り直してから合成する
[N:v]setpts=PTS-STARTPTS,format=rgba[wj];
```

同じ構文で合成しているカットすべてに影響するため、1箇所見つけたら**全生成器を確認する**こと。

## ループ素材にするとき(scripts/make_loop.py)

```bash
python3 scripts/make_loop.py 固定済み.mp4 loop.mp4 0.4
```

尾と頭を溶かして輪にする。**等速のまま**使うこと。

### やってはいけない2つ

**逆再生でのパリンドローム連結**は避ける。折り返しで動きが逆流し、水や煙のように向きのあるものでは継ぎ目の位置がはっきり分かる。

**`setpts` によるスロー再生**も避ける。コマを複製するだけなので、1.5倍で全体の33%が複製コマになり、10Hz の細かいカクつきが出る。「ゆっくり見せたい」は、撮影時にハイフレームレートで撮るか、諦めるかのどちらか。

この2つは厄介なことに、`find_jumps.py` でも `measure_shake.py` でも検出できない — **位置は動いていない**ため。判定には別の指標を使う:

```python
# 複製コマの割合(0% でなければスロー再生の疑い)
d = [abs(frame[i] - frame[i-1]).mean() for i in range(1, N)]
dup = sum(1 for v in d if v < median(d) * 0.25)
```

### ffmpeg の xfade を使わない理由

`xfade` は透過率が最後のコマで 1.0 に届かず、消えるはずの映像がわずかに残る。その残りが輪の境目で一気に消えるため、そこだけ画が跳ねる。`make_loop.py` は透過率を端点まで動かし、最後のコマを頭の映像そのものにする。

実測(那智の滝): 素材のコマ間変化 中央値1.49 / 最大3.03 に対し、境目は **xfade 4.10 → 自前 3.35**。

### 溶かさずに繋げないか、まず探す

被写体によっては、よく似たコマ同士を選べば溶かさずに繋げる。総当たりで最小差を求め、コマ間の自然な変化と比べる。同程度なら、そこで切って繋ぐのがいちばん綺麗。

ただし**水は決して同じ形に戻らない**。那智の滝では最小差 8.55(自然な変化 1.49)で、クロスフェードが必須だった。

### 最後に

素材の末尾は追跡精度が落ちやすい(被写体が画角から出ていく)。`measure_shake.py` で末尾だけ残差が大きければ、切り落としてから輪にする。**ループ長が変わったら、素材を参照している生成器側の秒数定数も必ず更新する**(参照位置がずれて静止画のように見える事故が起きる)。
